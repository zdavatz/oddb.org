# ODBA-Datenschaeden und ihre Reparatur

Vorfall-Historie und Regeln aus `CLAUDE.md` (ausgelagert am 02.09.2026). Neue Notizen zu diesem Teilsystem gehoeren hierher, nicht in `CLAUDE.md`.

### The pointer index pointed at an Array (`jobs/repair_pointer_index`, 31.08.2026)

- **`/show/reg/54880/seq/02/pack/002` had been a `SERVER_ERROR` in the Search Console since 03.05.2026**, and 500'd again in the crawler log of 30.08. and the generika log of 31.08. `View::Drugs::PackageComposite#init` died on `@model.sequence` — "undefined method 'sequence' for an instance of Array".
- **`Persistence::Pointer#resolve` asks the index first**, and `find_by_pointer(to_s) or begin … end` short-circuits on **any truthy value — an empty Array included**. The index row for that pointer led to a `Fachinfo`'s `@registrations` list, so the walk below never ran and the view got the Array.
- **The walk below is not a fallback, and that cost a wrong first fix.** `resolve` is called as `pointer.resolve(@session.app)`, and `ODDB::App` answers `respond_to?(:registration)` with **false** — it dispatches through `method_missing`. So the walk raises `InvalidPathError` on the very first step, for every pointer. Guarding the index hit and falling through therefore only traded `NoMethodError` for `InvalidPathError`; both are 500. The index is the only working path.
- **The fix is to take the right row, not to fall through.** `find_by_pointer` ends in **`.first` over a query with no `ORDER BY`** (odba `persistable.rb:119-137`), so with two rows Postgres decides which wins — which is exactly why the same url answered 500 three times and 200 minutes later with no restart, and why a crawler saw the error and a hand check did not. `resolve` uses `search_by_exact_pointer`, which returns **all** rows, and takes the first that `is_a?(Persistence)`.
- **Measured over all 603 288 index rows**: 30 led to an Array or Hash, 276 to an object that no longer exists (inert — `find_by_pointer` already returns nil for those; they are leftovers of the August `@sl_entry` and BAG-agent repairs). 306 deleted, and 306 → **0** afterwards.
- **Deleting a bad row does not by itself repair the page**, and only one of the 30 was a public page anyway. 29 of them name an object that is genuinely gone (compositions and inactive_agents addressed by `odba_id`, MiGeL items, substances) — verified by walking each pointer — so for those the walk finds nothing either. Only 54880/02/002 had a second, correct row next to the bad one. The code guard is what fixes the page; the job removes the noise.
- Regression tests: `test/test_util/persistence.rb` — the load-bearing one puts an Array *beside* the object and asserts the object is taken.

### Patinfos whose `@sequences` was not a list (`jobs/repair_patinfo_sequences`, 31.08.2026)

- `Patinfo#_sequence_delegate` calls `@sequences.first` for `company_name` and `name_base`. **24 of 14 554 Patinfos held a `PatinfoDocument` there** (one an `SlEntry`), and those pages answered 500 — `/de/gcc/patinfo/reg/56221/seq/03/pack/009` among them.
- **`object_connection` is the wrong source for this question, twice over.** A prefilter on "Patinfo with an edge to something that is neither Array nor Descriptions" gave 38 edges / 31 objects, of which **7 had a perfectly intact `@sequences`** — an edge does not say which ivar it came from. And a `@sequences` that is nil or dangling has no usable edge at all. Walking all 14 554 objects costs about a minute and is the only number that holds: **24**.
- **`instance_variable_get` on a Stub reads the Stub's own ivars** (`@odba_id`, `@odba_container`, `@receiver_loaded`, …) and cheerfully reports `@sequences` as nil. `odba_instance` first, then ask. This produced one wrong "0 broken" reading before it was noticed.
- Rebuilt from the sequences that point back, and only where `seq.patinfo` really is that Patinfo — the check `Patinfo#article_codes` already makes on itself with `next unless seq.patinfo == self`. **16 of 24** had exactly one; the other 8 got an empty list, which is enough to make the page live again.
- **Write order: the list first, alone, then the holder.** It is its own ODBA object and appears in the holder's dump only as a stub — get it wrong and a broken reference becomes a dangling one, the way it did once in `repair_dead_bag_agents`. `SequenceObserver#add_sequence` does it right and is reused. Verified by **re-reading in a fresh process**, not from the job's own report: 14 554 of 14 554 hold an Array, and all 24 reference a real list.
- **The code guard tries `.first` and rescues rather than asking `is_a?(Array)`** — a dangling stub *declaring* Array answers that question with yes and raises on the next line. The silence is deliberate and has a counterpart: the job counts them and mails from cron.
- **These 24 are damaged in a second ivar too**, and that is pre-existing and separate: 10 have a `@descriptions` that raises `ODBA::OdbaError`, 7 hold a document there. Patinfos never touched show the same (6, 6, and 15 nil), so it was not caused by the repair — but 17 of 24 against 12 of 14 530 says one event broke both ivars on the same objects. It does not crash (`SimpleLanguage#description` rescues and logs), it just leaves the drug without text. The repair for that is a reparse per registration, not a data edit.
- **What writes a document into `@sequences` is not known.** Every assignment in `src/` hands over an Array. The near-consecutive ids 57617341/347/350/473/829 look like one job that died partway — the same signature as the dead BAG agents — but that is a hypothesis, not a finding.
- Regression tests: `test/test_model/patinfo.rb`, both failing against the old code with the production error.

**What was left after all this** (replaying every distinct url that 500'd on 30. and 31.08.): **42 of 46 answer 200**. Of the four, `hospitallist/range/a-d` answered 500 cold and 200 on the second request — the intermittency above, not a separate bug. Two of the remaining three were the `@change_log` fault below; the last is a nil `@components` in `view/drugs/patinfo.rb:158` (10999/01/022), still open.

### `Fachinfo` had the guard, `Patinfo` never got it (`change_log`, 31.08.2026)

- `Session#request_path` calls `found.patinfo.send(language).change_log.select` for a `/show/patinfo/…/diff/…` url. **39 of 29 969 documents hold a `PatinfoDocument` in `@change_log`**, and `.select` on one raises `private method 'select' called for an instance of ODDB::PatinfoDocument` — 500 on the diff pages of 56908/01/017 and 57175/01/008, both confirmed to be exactly those documents.
- **`FachinfoDocument#change_log` has carried a "Safety check: if somehow @change_log got corrupted, reset it" for a long time. `PatinfoDocument#change_log` was the bare `@change_log ||= []`.** That asymmetry is the whole reason the failure shows up on Patinfo diffs and never on Fachinfo diffs — worth remembering as a search strategy: when one of the two classes is guarded, look at the sibling.
- **`nil` is not damage here**: 6911 of the 29 969 have none, and the reader answers `[]`. The FI change log starts 06.11.2015 and the PI one 22.08.2017; older documents never had one.
- The guard now probes instead of asking — `@change_log.is_a?(Array) && @change_log.length >= 0` inside a `begin/rescue`, because a dangling stub *declaring* `Array` answers `is_a?` from the declaration and only raises on the access. The Fachinfo one was hardened the same way, and its `puts` became `LogFile.debug`: a `puts` out of a web process lands unfiltered in the service log.
- **`odba_store`, not `odba_isolated_store`**, to persist the reset. The fresh `[]` is its own ODBA object; `odba_store_unsaved` walks `odba_unsaved_neighbors` and takes it along, while the isolated call would leave a dangling stub — the trap from `repair_dead_bag_agents`, and the one case where the non-isolated call is the correct one.
- The ids cluster in consecutive runs (57133525/526, 57133841/850, 58934175…269, 59171349…548), and **57133664 — one of the 24 Patinfos with a broken `@sequences` — sits inside the first run.** One event damaged both.
- No data repair was needed: the guard resets and persists on read, so each of the 39 heals the first time its page is opened.
- Regression tests: `test/test_model/patinfo.rb`, three of them, two failing against the old code.

### The nil `@components`, and the reparses that were not needed (31.08.2026)

- `PiChapterChooser#init` mixed the accessor `components` with the raw ivar `@components`. The accessor is `@components ||= COMPONENTS.dup`, and the `unless @model.pointer.skeleton == [:create]` block above is what calls it first — so with a **`[:create]` pointer** that block is skipped, the ivar stays nil, and `@components.store` at the end raises `undefined method 'store' for nil`. That was `/en/mobile/patinfo/reg/10999/seq/01/pack/022` (Osanit dentition), whose Patinfo never got a real pointer. Use the accessor; there is no raw `@components` left in the file. Regression test: `test/test_view/drugs/patinfo.rb`.
- **The 17 `valid?=false` Patinfos needed no reparse, and running one would have done nothing.** The claim that they did was wrong, and what disproved it was one walk: **0 of the 17 are reachable from any live registration**, while all 7 valid ones are. The names the repair job printed came from sequences found in `object_connection` — and 11 of those 16 sequences are **dead objects** that still carry a `registration` reference (69929, 68488, 69134, and one "59354001", which is not even a valid IKSNR) but do not appear in `reg.sequences`.
- **Every live sequence of those registrations has a `valid?=true` Patinfo with a real document** — Adempas, Tolison, Mekinist, Vyndaqel, Sitagliptin, Olmesartan, Berocca, Humira all have their texts. The 17 are orphans of superseded import generations, nothing links to them, and no page can render them.
- 69929 and 68488 are exactly the registrations whose pointer strings carried **70 and 36 index rows**. A registration re-imported that often leaves a generation of sequence, package and patinfo objects behind each time. That is the pattern to look for when a count of "broken" objects seems high: **ask whether anything still reaches them before repairing or reparsing.**

### Wo der Schaden herkam: zwei Prozesse, eine odba_id (`src/util/odba_id_patch.rb`, 31.08.2026)

- **Nichts schreibt ein Dokument in `@sequences`.** Die Array *wurde in der Datenbank ueberschrieben* von einem Dokument, dem ein zweiter Prozess dieselbe `odba_id` gegeben hat. Der Verweis im Ivar ist in Ordnung und zeigt auf die richtige Nummer - unter der Nummer liegt nur ein anderes Objekt. Deshalb ist die Suche nach der schreibenden Codestelle ergebnislos geblieben: es gibt keine.
- **`ODBA::Storage#next_id` war `@next_id += 1` unter einem Mutex**, und `@next_id` wurde **einmal beim Prozessstart** aus `SELECT odba_id FROM object ORDER BY odba_id DESC LIMIT 1` gesetzt. Der Mutex schuetzt innerhalb eines Prozesses. Hier laufen vier Rack-Backends, `ext/readonly` und jeder Job mit je einem eigenen Zaehler. Nachgemessen, zwei Prozesse nebeneinander: beide bekamen `[61935067, 61935068, 61935069]`.
- **`ODBA::Cache#next_id` hatte eine Sicherung, und eine einzige Zeile hat sie aufgehoben**: `peer.reserve_next_id id rescue DRb::DRbError`. Der Peer wirft `OdbaDuplicateIdError`, wenn die id schon vergeben ist - aber ein `rescue` ohne Klasse faengt jeden `StandardError` und liefert die Klasse als Wert. Das `rescue OdbaDuplicateIdError / retry` am Methodenende konnte nie greifen. **In 1.2.0/1.2.1 ist daraus ein Block-`rescue` geworden, immer noch ohne Klasse - ein Upgrade hilft nicht.**
- **`@file_lock` ist `false` und wird nirgends gesetzt** (`/tmp/count.ch_oddb` existiert nicht), also lief immer der prozesslokale Zweig.
- Die Reparatur: eine **Postgres-Sequenz** `odba_id_seq`, angelegt bei `MAX(odba_id) + 100000`. Der Abstand deckt ids ab, die laufende Prozesse noch im Speicher halten; uebersprungene Zahlen kosten nichts, die odba_id ist ein Surrogatschluessel. Dazu das `rescue` auf `DRb::DRbError` eingegrenzt, damit der Peer-Konflikt wieder zu einem neuen Versuch fuehrt.
- **`log/job.pid` deckt das nicht ab, und das ist der Denkfehler, der naheliegt.** `Util::Job.updater?` ist `basename.match(/^update|^import|^rebuild|^repair/)` - die Rack-Backends nehmen die Sperre nie (sie schreiben trotzdem: der change_log-Schutz, `SimpleLanguage#description`, das beim Lesen ein neues `Descriptions` speichert, Feedbacks, `create_patinfo`), `ext/readonly` geht gar nicht durch `Util::Job`, und `build_*`, `export_*`, `check_indexing` matchen den Ausdruck nicht. Die Sperre verhindert zwei Importer gleichzeitig, nicht einen Importer neben einer ausgelieferten Seite.
- **`ext/readonly/bin/readonlyd` laedt `util/oddbapp` nicht**, sondern `etc/db_connection` direkt - es haengt seit jeher mit eigenem Zaehler an derselben Datenbank und ist zugleich der DRb-Peer. Der `require` steht jetzt dort. Das ist auch das Argument fuer eine odba-Freigabe statt eines Monkey-Patch: der naechste Prozess, der so angelegt wird, bringt den Fehler still zurueck.
- **`yus` haengt an `odba (>= 1.1.6)`** und hat dieselbe Schwaeche, aber in seiner eigenen Datenbank (`dbname=yus`) - keine Kollision mit `ch_oddb`.
- Regressionstests: `test/test_util/odba_id_patch.rb`, sieben Stueck. Der tragende faellt gegen den Originalstand durch (erwartet 101, bekommt 100).

### odba 1.2.2 und 1.2.3, und warum der Shim bleibt (31.08./01.09.2026)

- Beide Korrekturen sind als **odba 1.2.2** veroeffentlicht (`github.com/zdavatz/odba`, Tag `v1.2.2`): `Storage#next_id` holt die id aus der Sequenz `odba_id_seq`, die `#setup` anlegt, und `Cache#next_id` faengt nur noch `DRb::DRbError`. Drei Tests, jeder faellt gegen 1.2.1 durch; Gesamtlauf 220 Tests, 0 Fehler.
- **Der Startwert der Sequenz wird berechnet und muss es**: ein blankes `CREATE SEQUENCE` beginnt bei 1 und vergibt ids neu, die es schon gibt. `MAX(odba_id) + ID_SEQUENCE_GAP`.
- **`Gemfile` steht seit dem 01.09.2026 auf `odba 1.2.3`** (31.08. auf 1.2.2), produktiv verifiziert (`id_sequence?=true`, Testlauf 3824/63 ohne neue Fehler). Beachte: ein blosses `bundle install` haette nie etwas geaendert - die Version ist exakt gepinnt, der Gemfile-Eintrag musste angefasst werden.
- **Der Sprung dorthin brauchte zwei Vorarbeiten.** 1.2.0 hat `lib/odba/18_19_loading_compatibility.rb` geloescht, und `oddbapp.rb` verlangte es - sofortiger `LoadError` in allen vier Backends. Die Datei liegt jetzt als `src/util/odba_18_19_compat.rb` unveraendert im Baum (77 Zeilen, aus 1.1.9 uebernommen); sie wird von den zwei nicht migrierbaren `Descriptions` weiter gebraucht. Und `src/util/odba_id_patch.rb` schaltet sich mit `return if ODBA::Storage.method_defined?(:id_sequence?)` selbst ab - er bleibt liegen, damit ein Rueckschritt auf 1.1.9 den Fehler nicht still zurueckholt und `readonlyd` seinen `require` behaelt.
- **Die Tests des Patch pruefen jetzt die Zusicherung statt der Umsetzung** (gibt es ueberhaupt eine gemeinsame Id-Quelle, fuehrt ein Peer-Konflikt zu einer neuen id) - die Umsetzung testet odba selbst. Sonst haetten sie nach dem Upgrade eine Attrappe geprueft und waeren gruen geblieben.
- 1.1.9 → 1.2.2 sind 3558 geaenderte Zeilen ueber 15 Dateien, fast alles der standardrb-Umbau von 1.2.0 - dieselbe Form, in der bei sbsm 1.6.3 die Sanitisierung verschwand. Der volle Testlauf und ein Bootlauf gegen die echte Datenbank sind hier das Mindeste, bevor neu gestartet wird.
- **`18_19_loading_compatibility` heisst irrefuehrend und darf nicht weg, obwohl wir auf Ruby 3.4 sind.** Es ist kein Shim, um *unter* 1.8/1.9 zu laufen, sondern um *Daten zu lesen, die dort geschrieben wurden*: es definiert `Date._load` und `Encoding::Character::UTF8._load`. Gemessen in `object`: **4217 Dumps im alten `u:\tDate`-Format** (Ruby 3.4 schreibt `U`, also `marshal_load`, und das ist vom Shim unberuehrt) und **129 mit `Encoding::Character::UTF8`** (83 `Text::Chapter`, 43 `InvoiceItem`, 2 `Descriptions`, 1 `LimitationText`). Nachgestellt: dasselbe Objekt laedt mit Shim als `ODDB::Text::Chapter` und ohne ihn mit `ArgumentError: undefined class/module Encoding::Character::UTF8`.
- **`jobs/rewrite_legacy_dumps` hat das am 31.08.2026 gemacht: 4341 von 4346.** Vorher ein `pg_dump -Fc` (3.8 GB, 15 min; am 01.09.2026 geloescht, nachdem die Migration verifiziert war), die alten Dumps stehen vollstaendig in `log/rewrite_legacy_dumps-*.undo` (16 Dateien, 140 MB, 4479 Zeilen - das feinere Netz, weil es je Objekt zurueckholt statt der ganzen Datenbank) - ein Marshal-Format laesst sich nicht zurueckrechnen, der Sicherungsschritt ist hier wichtiger als bei den anderen Reparaturen.
- **Die alte Zeichenkette ist keine Instanz von `Encoding::Character::UTF8`**, und das hat den ersten Anlauf kosten lassen: der Dump traegt Marshal-Typ **`e`** - ein String, der mit dem Modul `Encoding::Character::UTF8::Methods` **erweitert** wurde, wofuer der Shim dieses sonst leere Modul ueberhaupt definiert. `o.class` ist `String`, eine Suche nach der Klasse findet nichts, und `odba_isolated_store` schreibt die Erweiterung unveraendert zurueck - der Dump kam Byte fuer Byte gleich wieder. Erst ein Durchlauf durch den Objektgraphen, der solche Strings per `dup` ersetzt (`dup` uebernimmt die Singleton-Klasse nicht), wird sie los. Gefunden wurde das nicht durch Lesen, sondern indem die Bytes um den Marker herum dekodiert wurden.
- **Der Index bleibt unberuehrt, und das wurde geprueft, nicht angenommen**: beim Schreiben der 356 Registrierungen meldete ODBA `undefined method 'values' for nil when updating index 'sequence_vaccine'` (ein vorbestehender Defekt der Indexdefinition - `origin.sequences` ist bei manchen nil). `sequence_vaccine` aus dem *vor* der Migration gezogenen Dump gegen die laufende Tabelle: 263 Zeilen hier wie dort, Inhalt identisch.
- **Fuenf bleiben liegen, mit Grund.** 3 `IncompleteRegistration` - die Klasse gibt es nicht mehr, die Zeilen werfen `undefined class/module` mit *und ohne* Shim, halten also niemanden auf.
- **Die zwei `SimpleLanguage::Descriptions` sind keine Waisen, und die gegenteilige Notiz war ein Lesefehler von mir** (in der eigenen Pruefung eine odba_id vertippt und das "false" als Beleg genommen). Es sind die `@descriptions` von zwei ATC-Richtliniendokumenten: **27827703** haengt an `Text::Document` 1121393 → `AtcClass` **A10BB** (Sulfonylharnstoff-Derivate, `ddd_guidelines`), **27829500** an 1122154 → **B03A** (Eisen-haltige Zubereitungen, `guidelines`).
- **Die Daten sind heil.** Ueber das Modell gelesen kommt der richtige WHO-Text zurueck ("The DDD for micronized glibenclamide is lower comp…", "This group comprises all plain iron preparations a…"), und `/de/gcc/atc/A10BB`, `/B03A`, die franzoesische Fassung und der ATC-Browser antworten 200. Die beiden **Eltern-Dokumente sind bereits sauber** (752 und 742 Bytes, keine alte Form) - nur die zwei Kinder tragen die String-Erweiterung noch.
- **Sie sind genau der Grund, warum der Shim bleibt.** Roh geladen: mit Shim `ODDB::SimpleLanguage::Descriptions`, ohne ihn `ArgumentError: undefined class/module Encoding::Character::UTF8`. Das ist kein Datenschaden, sondern eine Datei von 77 Zeilen, die wir behalten.
- Offen bleibt nur noch die enge Frage, **warum `odba_isolated_store` diese zwei Zeilen Byte fuer Byte gleich laesst**. Folge davon ist ausschliesslich, dass der Shim liegen bleibt - was ohnehin nichts kostet.
- **Der Shim kann also noch nicht weg**: solange die zwei `Descriptions` da sind, kostet sein Entfernen genau diese zwei Objekte. Er liegt seit dem Upgrade als `src/util/odba_18_19_compat.rb` im Baum, nicht mehr im Gem.
- **`--verify` taugt nicht als Freigabe, und das war zuerst falsch aufgeschrieben.** Der Lauf meldet fuer alle fuenf Reste "ok" - auch fuer die drei `IncompleteRegistration`, deren Klasse es nicht mehr gibt. ODBA faengt den Ladefehler in `fetch_or_restore` selbst ab und liefert etwas zurueck, statt ihn durchzureichen. Wer den Shim wirklich entfernen will, muss die Objekte roh laden (`Marshal.load` auf `object.content`) und nicht ueber `ODBA.cache.fetch` gehen.

### The eight dead ActiveAgents, and where they came from (`jobs/repair_dead_bag_agents`, 29.08.2026)

- **The cause was still in the code, in both BSV importers.** `add_bag_composition_to_sequence` cleared the old agents by hand before writing the new ones, and did it three ways wrong at once: it iterated the very list `delete_active_agent` deletes from (so with two agents the second is never visited), it called `agent.odba_delete` **unconditionally** — also when `delete_active_agent` had found nothing and left the reference standing, which is exactly how a dangling stub is made — and once one was in the list, every comparison over it threw, because `Array#delete` compares with `==` and `ActiveAgentCommon#==` calls `.substance` on the other side. That throw disappeared into the method's own `rescue => e` / `LogFile.debug`, so **the composition was simply never updated again**. Both plugins call `Composition#delete_all_active_agents` now.
- Repaired: 7 dead agents in the BAG compositions of 53662/01, 53662/02, 53663/02, 14825/03, 65069/01, 66687/01, 67064/01, plus `@active_agents = nil` on 69144/01. Measured over all 15018 registrations, nothing else. Undo log in `log/repair_dead_bag_agents.undo`.
- **Nothing could be restored, and that is a property of the data**: the BAG compositions carry no `source` text, unlike the Swissmedic ones that `jobs/repair_broken_active_agents` rebuilds from. The next BSV import writes new agents as soon as the drug is in the SL again.
- **`@inactive_agents` is nil on 6885 compositions and that is not damage** — Hilfsstoffe were introduced in 2015, everything older never got the ivar, and the reader answers `[]`. The job reports it and leaves it alone; normalising it would be 6885 writes for nothing. Only `@active_agents` is repaired. The code that reaches for the ivar directly was fixed instead — see the next section.
- **Setting the ivar and storing the holder made it worse, once.** `comp.instance_variable_set(:@active_agents, [])` plus `comp.odba_isolated_store` traded a harmless nil for a **dangling `Array` stub** (61910219): the list is its own ODBA object with its own `odba_id` and is replaced by a stub in the holder's dump, so it has to be stored **first**, by itself. Same trap as the change_log in `repair_orphaned_change_logs`. Visible only by re-reading in a fresh process — the job's own run reported success.
- **`is_a?(Array)` passes for that stub too.** A dangling list declaring `Array` answers `is_a?(Array)` without resolving, and only the next real method call raises. There is no cheap guard for this anywhere.
- Regression tests: `test/test_model/composition.rb` — `test_delete_all_active_agents` fails with the old loop (both agents still in the list after the objects were deleted), `test_delete_all_active_agents__with_a_dead_one` fails with `ODBA::OdbaError`. Both mechanisms, one test each.

None of this repairs the underlying data; it stops one broken reference from taking a whole page down. And the biggest single cause was not code at all: three rack backends were dead for 9.7 to 18.6 days while `svstat` reported "up".

**Beware of measuring through `:443`.** Anubis answers `curl` with a 500 and an "Oh noes!" page while serving browsers normally, so a redirect chain tested with curl can look like it ends in a server error when it does not. Either send a Googlebot user-agent, which bypasses Anubis, or probe `http://localhost:8012` directly. This has now cost time twice.

### Orphaned change logs (`jobs/repair_orphaned_change_logs`)

- **A `change_log` hangs on the document, not on the drug.** `@change_log` is an ivar of `FachinfoDocument` / `PatinfoDocument` (`src/model/patinfo.rb:76-128`), and every FI/PI update creates a *new* document. `store_fachinfo` and `store_patinfo_change_log` carry the list over; where they don't, the whole history is cut loose at once. In August 2026 **31447 of 125403 change log items** were unreachable — a quarter of the diff history, over 3973 drugs, median 4 per drug and up to 140.
- **The drugs are all still there.** 0 of 15549 `Registration`, 0 of 24895 `Sequence`, 0 of 14548 `Patinfo` unreachable. What is orphaned are superseded *versions of the texts*. On a page it looks like a clean cut at a date: `/show/fachinfo/51886/diff` listed 7 revisions from 14.08.2017 on, and 61 from 15.11.2015 to 12.08.2017 lay unreachable beside them.
- **Every FI and PI carries its own registration number**, at the end of the text ("Zulassungsnummer 12345 (Swissmedic)"), and `Diffy::Diff` stores the complete old *and* new text — so an orphaned entry can be attributed from its own content. 29088 of 31447 yield a number that way. The same double storage is what makes the database 19 GB.
- **The verdict is a check against the target**, not the extraction: does the document's own text carry the same number? 20167 confirmed, 721 not — and those are typically neighbours like 59410 against 59411, the same substance in another strength, whose texts resemble each other. A regex alone would have attached them to the wrong drug.
- **Two steps, so what gets written is reviewable.** `--plan` writes `item, document, verdict`; `grep` filters; `--from-plan --apply` attaches exactly those pairs and decides nothing again. Appending only, never deleting, and every pair goes to a `.undo` file.
- **`odba_isolated_store` on a document does not write its `change_log`.** The list is a separate ODBA object with its own `odba_id` and is replaced by a stub in the document's dump (`odba_replace_persistables`), so it has to be stored itself, *before* the document. Getting this wrong yields a run that reports 20107 written and changes nothing — visible only by re-reading in a fresh process, never from the job's own success report.
- **The database already holds that mistake**: 7614 edges in `object_connection` point at an `odba_id` with no row in `object` — 4091 from `Package`, 1732 from `Hash`, 1120 from `SimpleLanguage::Descriptions` (the empty Patinfos), 272 from `FachinfoDocument2001`. Where a document's `change_log` stub dangles, reading it raises `ODBA::OdbaError` and the page is dead; the repair recreates the list, since nothing can be lost that was never written.
- **Verifying orphanhood needs two independent methods**, because a single one only proves the model. A recursive BFS over the 7373917 edges from the named, `prefetchable` and index-referenced roots, and a walk through all 14996 live registrations collecting every reachable change_log id. The 93946 the walk found and the 31447 the search called orphaned did not overlap in one single case. **Do not put `object_connection` in the root set** — it has a `target_id` column too, so an `information_schema` query picks it up and every object with any incoming edge becomes a root.
- Result: 20105 reattached, orphans down from 31447 to 11340. Still open: 2948 registrations with several distinct `Patinfo` objects (ambiguous, skipped), 2359 with no number in the text, 1289 with no target document left, 721 doubtful.
- **The cause, found 26.08.2026**: `PatinfoDocument#add_change_log_item` compared the new diff against the existing ones to skip duplicates, and the rescue around that comparison read `@change_log = [item]`. Comparing calls `x.diff.to_s`, which runs Diffy, which writes two tempfiles and shells out to `diff` - where this data's encoding trouble lives. So **one entry that stumbled replaced the whole change log with the single new item**, and everything before it stayed in the database with nothing pointing at it. The Fachinfo version of the same method only logs and leaves the list alone, which is why 26293 of 55993 PI items are unreachable against 5154 of 73090 FI items, and why a history breaks off cleanly at a date instead of thinning out.
- **How it was found matters more than the bug.** Three explanations were reasoned out and all three died on measurement - the `instance_of?` subclass bug reaches 64 objects, a January 2026 correlation spans 144 drugs against 15 logged deletions, and a pre-2018 lull was an artefact of a partial inventory. What worked: snapshot every reachable `change_log` id per registration, wait for one `update_today`, snapshot again, diff. **2 entries gone out of 22 Patinfos stored**, both `PI de`, both on a drug whose German text had just been rewritten. Two per day over twenty years is the order of magnitude. The snapshot script is worth rebuilding if a similar question comes up: it is a walk over all 14996 registrations collecting ids, nothing clever.
- **Restoring is a different question from stopping.** The fix loses nothing further; it recovers nothing either. **47 `Patinfo` objects over 40 registrations** have no document at all, 40 of them active - Anexate, Sandostatin, Actemra among them. Only **5** of those registrations have an orphaned diff whose `@string2` still holds the text; the other 36 need a reparse from swissmedicinfo (`jobs/update_textinfo_swissmedicinfo --skip --target=both <IKSNR> --reparse`), which is the better repair anyway because it restores the *current* text rather than an old one. Issue #446.
- **An earlier count said "7710 empty Patinfos" and was wrong.** It walked `object_connection`, whose edges are not the application's access path - the same trap as the ATC guidelines. The walk through live objects finds 47. When a number about this data matters, get it by walking the objects, not by joining the edge table.
- **The old cause note, kept because the failures are instructive:**  Three attempts failed: the `instance_of?` subclass bug in `fix_odba_error_in_patinfo` (`PatinfoDocument2001` exists 64 times in the whole database, so it cannot explain the mass), a January 2026 correlation with the deletion log (310 orphans over 144 drugs against 15 logged deletions), and an assumed pre-2018 lull that the complete inventory disproved. The loss runs continuously from 2015 (417) to 2025 (5386). A snapshot of every reachable change_log id per registration is in place to be compared after the next `update_today`.

### The 7.5 GB nobody could reach (`jobs/delete_unreachable_objects`, 27.08.2026)

- **Every update of a Fach- or Patinfo left the old document behind.** `SimpleLanguage#update_values` puts the parser's new document where the old one stood in `@descriptions`, and nothing deleted the old one — with its ~20 chapters. On ~6300 live Fachinfos that had grown to **200 000 superseded document versions and 3 953 085 chapters**, 7.5 of 19 GB, roughly 20 000 documents a year. Same mechanism as the orphaned change logs.
- **Measured twice, and that is the point.** A breadth-first walk of `object_connection` from the named, the `prefetchable` and the index-referenced objects said 1 944 217 of 7 114 259 are reachable. `jobs/verify_chapter_reachability` walks the **live objects** instead — registrations → fachinfo/patinfo → documents → chapters — and reached 286 639 chapters, **not one** of them in the set the search calls unreachable. The same search returns exactly the 11 340 orphaned `ChangeLogItem`s the August repair left behind, which is what makes it trustworthy.
- **The first verification run was worthless and looked perfect.** It reported 1261 chapters and "0 Widersprüche". `reg.fachinfo` and `fi.de` hand back an **`ODBA::Stub`**, whose own instance variables are only `@odba_id`, `@odba_container`, `@odba_class`, `@receiver_loaded` — a walk over `instance_variables` finds nothing and reports calm. Only a method call resolves the stub. And the chapters are not ivars at all: `document.chapters` returns **symbols**, the names, and `document.send(name)` is what yields the chapter. The corrected run reached 286 639.
- **`ChangeLogItem`, `Array` and `Hash` are never deleted.** 31 370 diffs hang on those old documents, 20 105 of them reattached to live documents in August and visible on the `/diff/` pages today. `Array` holds the change_log lists. Losing those would have cost a quarter of the diff history.

But it does a query per object and rewrites every referrer, which is hours for four million; the deletion runs as batched SQL instead, and is therefore **not reversible**. - **`EphaInteraction` went too, all 207 490.** The class was removed on 11.03.2026 with "Replace EPHA CSV interactions with SDIF SQLite database" — `defined?(ODDB::EphaInteraction)` answers nil, so nothing could load one even in principle. - Result: 4 399 175 objects deleted in seven stages (smallest class first, restart and page probe after each), objects 7 114 259 → 2 715 084, and after `VACUUM FULL` (2 min 8 s, exclusive lock, site unreachable meanwhile) the database went **19 GB → 9.66 GB**. Every id is logged to `log/deleted_unreachable-<timestamp>.txt`.

### The superseded document is deleted now (`src/util/superseded_document.rb`)

- Without this the 7.5 GB come back at ~20 000 documents a year. The hook is in **`SimpleLanguage#update_values`**, the one place both Fachinfo and Patinfo pass through, plus `TextInfoPlugin.replace_textinfo`, which writes into `descriptions[lang]` directly and would otherwise slip past.
- **Nothing is lost, and that is why it is allowed**: `store_fachinfo` carries the `change_log` into the new document, and a `Diffy::Diff` stores the complete old **and** new text. Every change_log entry is a whole version by itself — which is also why the old documents were redundant rather than historical. Measured on three drugs: the unreachable document carried *the same* date range as the live one, not an older one.
- **The change_log is taken out of the old document before it falls**, rather than trusting that delete does not cascade. And **a chapter the successor also uses survives** — the parser builds each chapter anew, but that is an assumption about `ext/fiparse`, and a wrong one would cost a live drug its text.
- Verified end to end with a reparse of 57192: document 61893094 / 19 chapters / 9 diffs before, document 61894333 / 19 new chapters / the same 9 diffs after, and 61893094, 61893115 and their chapters gone from the database. Tests: `test/test_util/superseded_document.rb`, `test/test_util/language.rb`.

### Dangling ODBA references (`jobs/repair_dangling_references`)

- **`checkout` deleted the child and kept the reference.** `Package#checkout` called `odba_delete` on `@sl_entry` and `@parts` and cleared neither, so the package held a stub to an object that no longer existed. **3950 packages** for `@sl_entry`, 141 for `@parts`. `Sequence`, `Registration` and `Composition` had the same shape (`@packages`, `@compositions`, `@sequences`, `@active_agents`). All four fixed August 2026; `delete_sl_entry` twenty lines below in `package.rb` had always done it right and is the model.
- **No `odba_isolated_store` in `checkout`.** It runs immediately before or after the `odba_delete` of the object itself (`util/persistence.rb:283-291`, `model/sequence.rb:124`), so storing would recreate what was just deleted. Clearing the ivar is the whole fix.
- **Why it stayed invisible for years:** only `limitation` and `limitation_text` go through `@sl_entry`. Price, deductible, generic type and name come from other fields, so the pages answered 200 and only the limitation was missing — 292 of 300 sampled packages raised `ODBA::OdbaError` on it. A 500 would have been found sooner.
- **Clearing, not restoring, is the right repair here**: of 3924 affected packages only **135** are still in the BAG NDJSON, the other 3789 have left the Spezialitätenliste. The reference was not just broken but moot, and a package that returns to the SL gets `@sl_entry` set again by the next BSV import.
- Result: 4410 objects cleaned, dangling edges 7502 → 3258, `limitation` answers on 300 of 300. Among them 257 `@connection_keys` on `Substance` — an ivar that appears nowhere in `src/`, `ext/` or the odba gem any more, a fossil.
- **Restricted to `ODDB::` classes.** The dangling edges also cover ODBA's own `@rebuilt`, `@failures`, `@to_drop`, `@deffered_indices` on index objects; those belong to `jobs/rebuild_indices`.
- **The 1120 `SimpleLanguage::Descriptions` are left alone** and that is deliberate: their broken links are hash entries rather than ivars, and `Text::Document` declares `@descriptions` as `ODBA_SERIALIZABLE` (`src/model/text.rb:613`), so the field is written inline and the separate objects are a fossil nobody follows. 6652 probes of `guidelines` / `ddd_guidelines` over all 8911 ATC classes raised nothing, and 120 ATC pages answered 200. **A dangling edge in `object_connection` is not proof of a broken page** — check whether the code still takes that path.
- Tests: `test/test_model/package.rb#test_checkout`, `test/test_model/composition.rb#test_checkout`. The composition one used to assert `checkout`'s return value, which happened to be `odba_delete`'s; it asserts the empty list now.

### rebuild_indices (`jobs/rebuild_indices`, nightly 01:19)

- **It failed on six indices every night from at least 01.01.2026 to 26.08.2026** — all 225 nights the debug log covers — and nobody saw it, because the cron lines ended in `>/dev/null 2>&1` until 24.08.2026. `substance_index_atc` had **no table at all**: the index is dropped before the rebuild, and the rebuild never finished. Issue #447.
- **Three unrelated causes.** (1) `searchterms.rb` guarded against `ASCII_8BIT` and `valid_encoding?`, and an **ISO-8859-1** string answers "no" and "yes" — in Latin-1 every byte sequence is valid — so it passed untouched into `/[[:punct:]]/u` and raised `incompatible encoding regexp match`. Encoding must be **converted** here, not relabelled; `force_encoding` is right only for `ASCII_8BIT`, where UTF-8 bytes sit without a label. `to_utf8` also handles frozen strings, which the old `unless term.frozen?` skipped entirely. Four indices, plus `indication_index` on `"\xC3" from ASCII-8BIT`. (2) **One corrupt object out of 41801**: a composition held an empty `Array` where an `ActiveAgent` belongs, and `substance_index_atc` / `substance_index_sequence` call `.substance` on *every* element — so one bad element costs the **whole index**. (3) `substance_index_sequence` used `resolve_target: 'active_sequences'`, a method that exists on `OddbPrevalence` and not on `Substance` (correct as `init_source`, wrong as `resolve_target`).
- **A broken reference passes `is_a?`.** `ODBA::Stub#is_a?` answers from the declared class **without resolving**; only `respond_to?` resolves and tells the truth. That is why the bad element looked like an `ActiveAgent` everywhere except where it was used.
- **You cannot delete it by value.** `Array#delete` compares with `==`, which for a stub goes through `ActiveAgentCommon#==` and calls `.substance` on the other element — precisely the broken one. Use `object_id`: it is on ODBA's `no_override` list (`stub.rb:83`), `equal?` is **not** and would resolve the stub. standardrb suggests `equal?` here; that suggestion is wrong and is disabled in place with the reason.
- `jobs/repair_broken_active_agents` rebuilds such elements from the composition text **by position**, and refuses to act unless the intact neighbours sit where the text puts them. Both `resolve_origin` expressions are guarded now, so one bad element can never cost an index again. Tests: `test/test_util/searchterms.rb`.

### Ein abgeschossener Job ist kein Plugin-Fehler (01.09.2026)

- `Updater#wrap_update` fing `rescue Exception` und schickte deshalb auch `SignalException`, `Interrupt` und `SystemExit` durch `notify_error`. Ein `kill` auf einen Job erzeugte damit eine Mail **"Error: swissmedic"** mit `Plugin: ODDB::SwissmedicPlugin` und einem Backtrace, der genau dort endete, wo der Prozess zufaellig stand — am 01.09.2026 im HTTP-Lesen von `SwissmedicPlugin#get_latest_file`. Das liest sich wie ein kaputter Swissmedic-Import und war keiner: der Lauf 30 Sekunden spaeter endete mit exit 0 und stellte korrekt fest, dass Swissmedic noch die Datei vom 06.08. liefert (byte-gleich, 3274214 Bytes).
- Die drei Signalklassen werden jetzt **vor** `rescue Exception` gefangen, protokolliert und **weitergeworfen** — ohne Mail. Das Weiterwerfen ist wesentlich: der aeussere blanke `rescue` nimmt nur `StandardError`, also beendet das Signal den Job weiterhin. Jede echte Plugin-Ausnahme wird gemeldet wie bisher.
- standardrb meldet dafuer `Lint/ShadowedException` — ein Fehlalarm, weil `Exception` *nach* den drei Signalklassen steht und weiterhin alles uebrige faengt. Vor Ort abgeschaltet, mit Begruendung.
- **Wer das SIGTERM geschickt hat, sagt kein Log.** Weder cron noch `oddb_cron healthcheck` schicken je TERM an einen Job — der healthcheck kennt nur die vier Rack-Dienste. Es bleibt das Terminal bzw. `screen` oder ein `kill` von Hand.
- **Der abgebrochene Download hat nichts Halbes hinterlassen**, und das ist der Punkt, an dem es haette teuer werden koennen: eine abgeschnittene `Packungen-*.xlsx` auf einer Seite des Vergleichs erzeugt genau den `SwissmedicDiff SUSPECT`-Massendiff, der im Juli den med-drugs-Export ruiniert hat. `get_latest_file` schreibt die datierte Datei erst, wenn sie sich von `Packungen-latest.xlsx` unterscheidet.
